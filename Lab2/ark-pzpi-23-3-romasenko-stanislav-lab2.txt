3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Архітектурні рішення та моделі системи
Серверна частина системи RoomBook побудована за принципами багатошарової архітектури, що забезпечує чітке розділення відповідальності між компонентами системи. Програмне рішення (Solution) розділено на три основні проєкти:

RoomBookSolution/
├── RoomBook.API/     # Рівень представлення (Presentation Layer)
│   ├── Controllers/       # REST-ендпоінти для взаємодії з клієнтами
│   ├── Hubs/                # SignalR хаби для IoT-комунікації (Real-time)
│   └── Program.cs       # Точка входу та DI-контейнер
├── RoomBook.Core/    # Ядро системи (Domain & Logic Layer)
│   ├── Entities/              # Сутності бази даних (User, Room, Booking)
│   ├── Interfaces/              # Абстракції для репозиторіїв та сервісів
│   └── Models/                  # DTO та доменні моделі
└── RoomBook.Infrastructure/    # Рівень інфраструктури (Data Layer)
    ├── Data/                    # RoomBookDbContext та EF Core міграції
    └── Repositories/            # Реалізація доступу до MS SQL Server
Характеристика архітектурних компонентів:
•RoomBook.Core (Domain Layer): Центральний проєкт, що містить бізнес-об'єкти та правила системи.
▪User: опис користувачів, їхніх ролей (Admin, User) та даних для авторизації.
▪Room: технічні характеристики приміщень та IotDeviceId для зв'язку з апаратним забезпеченням.
▪Booking: логіка бронювання, що включає перевірку часових інтервалів (StartTime, EndTime). Цей шар не залежить від жодних зовнішніх бібліотек, що робить бізнес-логіку легкою для тестування.
•RoomBook.Infrastructure: Відповідає за технічну реалізацію доступу до даних. Тут налаштовано Entity Framework Core та створено RoomBookDbContext. Використання патерну Repository дозволяє інкапсулювати складну логіку фільтрації та пошуку вільних кімнат у SQL Server, не перевантажуючи бізнес-логіку.
RoomBook.API: Зовнішній шар системи. Він використовує контролери для обробки HTTP-запитів та повернення відповідей у форматі JSON. Для інтеграції з IoT-модулями використано бібліотеку SignalR, яка забезпечує миттєву передачу команд на розблокування дверей без необхідності постійного опитування сервера клієнтом.
3.2 UML-діаграма прецедентів
Діаграма описує взаємодію двох основних акторів: Користувача та Адміністратора з серверною частиною.
•Користувач: авторизується, шукає вільні кімнати за фільтрами, створює та скасовує бронювання.
•Адміністратор: керує реєстром кімнат та обладнання, переглядає звіти про використання приміщень.
•Система (IoT Client): автоматично отримує команди на розблокування дверей при старті валідного бронювання.

3.3 Проєктування та нормалізація бази даних
Фізична модель БД реалізована в MS SQL Server. Для забезпечення цілісності та відсутності надлишковості проведено нормалізацію:
На етапі 1NF ми усуваємо повторювані групи. Якби ми зберігали дані в одній таблиці, поле Equipment містило б рядок через кому ('Projector, Whiteboard'), що порушує атомарність. Ми виносимо обладнання в окрему таблицю RoomEquipment.
1.Перша нормальна форма (1NF): Усі поля атомарні. Списки обладнання винесені у зв'язну таблицю RoomEquipment.

Рисунок 1 - 1NF. Розділення на атомарні дані
2.Друга нормальна форма (2NF): Видалено часткові залежності. Всі неключові поля в RoomEquipment (наприклад, Quantity) залежать від повного композитного ключа {RoomId, EquipmentId}.

Рисунок 3 - 2NF. Видалення часткових залежностей
3.Третя нормальна форма (3NF): Видалено транзитивні залежності. Дані про користувача (ім'я, пошта) не дублюються в таблиці Bookings, а зберігаються лише в Users.

3.4 Розробка функцій роботи з БД (ORM)
Взаємодія з БД реалізована через Entity Framework Core 8 (підхід Code-First).
•CRUD операції: Реалізовані через загальні та спеціалізовані методи репозиторіїв.
•Eager Loading: Використання .Include() для завантаження пов'язаних сутностей (наприклад, завантаження об'єкта Room разом із Booking), що мінімізує кількість запитів до БД (проблема N+1).

3.6 Реалізація логіки IoT-клієнта
Обов'язковою умовою було впровадження IoT-клієнта.
•Технологія: Використано SignalR (WebSockets) для підтримки постійного з'єднання між сервером та апаратним модулем.
•Логіка: При виконанні CreateBookingAsync у репозиторії, викликається IIotService. Завдяки впровадженню залежностей (DI), репозиторій не знає про деталі реалізації SignalR, що зберігає чистоту архітектури.

В.2 Логіка взаємодії з БД (Repository Pattern)
Метод створення бронювання містить логіку перевірки конфліктів та ініціацію команд для модуля доступу.
public async Task<bool> AddBookingAsync(Booking booking)
{
    var isOverlap = await _context.Bookings.AnyAsync(b => 
        b.RoomId == booking.RoomId &&
        b.StartTime < booking.EndTime && 
        booking.StartTime < b.EndTime);
    if (isOverlap) return false;
    await _context.Bookings.AddAsync(booking);
    await _context.SaveChangesAsync();
    if (booking.StartTime <= DateTime.UtcNow)
    {
        await _iotService.UnlockRoomAsync(booking.RoomId);
    }
    return true;
}
В.3 Програмна реалізація API (Controllers)
Контролер обробляє HTTP-запити та повертає стандартизовані коди відповідей.
// API/Controllers/BookingsController.cs
[ApiController]
[Route("api/[controller]")]
public class BookingsController : ControllerBase
{
    private readonly IBookingRepository _repository;
    public BookingsController(IBookingRepository repository) 
        => _repository = repository;
    [HttpPost]
    public async Task<IActionResult> Create([FromBody] Booking booking)
    {
        var result = await _repository.AddBookingAsync(booking);
        
        if (!result)
        {
            return Conflict(new { message = "Кімната вже заброньована на цей час" });
        }
        return CreatedAtAction(nameof(GetById), new { id = booking.BookingId }, booking);
    }
}
В.4 Реалізація IoT-шлюзу (SignalR Hub)

// API/Hubs/IotHub.cs
public class IotHub : Hub
{
    public async Task JoinRoomGroup(string deviceId)
    {
        await Groups.AddToGroupAsync(Context.ConnectionId, deviceId);
    }
    public async Task SendCommand(string deviceId, string command)
    {
        await Clients.Group(deviceId).SendAsync("ReceiveCommand", command);
    }
}
